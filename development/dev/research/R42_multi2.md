▎ Under GDPR, if a B2B hosting platform's own admin dashboard displays or manages another company's end-users' personal data (emails, ban status, session activity) — obtained via that hosted application's own auth library's official admin API, not raw database access — does the hosting platform likely become a joint controller, or does it remain a data processor/sub-processor of the hosted company? What contractual terms (DPA — Data Processing Agreement) are typically required for this specific scenario (a PaaS/hosting platform with programmatic admin access into a customer's own end-user auth system)? Are there existing DPA templates or legal guidance specifically covering "platform has admin API access to customer's own end-user data," as opposed to the more common "platform only stores encrypted customer application data at rest"?

Hier ist die datenschutzrechtliche Einordnung (DSGVO) für dieses spezifische PaaS/Hosting-Szenario, aufgeteilt in die rechtliche Rolle, vertragliche Anforderungen und die Praxis der Datenverarbeitungsverträge (DPA).1. Rechtliche Rolle: Joint Controller oder (Sub-)Processor?Die Hosting-Plattform bleibt in diesem Szenario ein Data Processor (Auftragsverarbeiter) bzw. Sub-Processor (Unterauftragsverarbeiter). Sie wird nicht zum Joint Controller (gemeinsam Verantwortlichen). [1] (https://www.back4app.com/product/parse-gdpr), [2] (https://www.wsiworld.com/blog/responsibilities-of-a-controller-processor-and-data-protection-officer-according-to-gdpr), [3] (https://www.legiscope.com/blog/gdpr-data-controller-vs-processor.html)Der entscheidende Faktor (Zweck und Mittel): Nach den Leitlinien des Europäischen Datenschutzausschusses (EDSA/EDPB) wird man nur dann zum (Joint) Controller, wenn man über die Zwecke („Warum wird verarbeitet?“) und die wesentlichen Mittel („Welche Daten werden von wem erhoben?“) der Verarbeitung entscheidet. [1] (https://www.legiscope.com/blog/gdpr-data-controller-vs-processor.html)Warum Sie Processor bleiben: Dass Ihre Plattform über ein Admin-Dashboard personenbezogene Endnutzerdaten (E-Mails, Sperrstatus, Sitzungen) anzeigt und manipuliert, dient ausschließlich dem Zweck, Ihrem B2B-Kunden die Verwaltung seines Dienstes zu ermöglichen. Sie tun dies auf dokumentierte Weisung des Kunden. [1] (https://usercentrics.com/knowledge-hub/gdpr-controller-vs-processor/), [2] (https://sprinto.com/gdpr/data-processor/), [3] (https://www.manageengine.com/compliance-manager/gdpr-compliance/gdpr-chapter-4.html), [4] (https://www.legiscope.com/blog/gdpr-data-controller-vs-processor.html)Wann die Grenze überschritten wird: Sie würden erst dann zum Controller werden, wenn Sie diese über die API erlangten Daten für eigene Zwecke nutzen würden (z. B. für plattformübergreifendes Benchmarking, eigene Nutzerprofile oder KI-Modelltraining). Da dies nicht der Fall ist, bleibt die Rollenverteilung strikt: Ihr B2B-Kunde ist Controller, Sie sind Processor. [1] (https://www.flosum.com/blog/gdpr-compliance-for-saas-platform-owners), [2] (https://www.legiscope.com/blog/gdpr-data-controller-vs-processor.html), [3] (https://payproglobal.com/answers/what-is-dpa-agreement-in-saas/)2. Typische vertragliche Klauseln (DPA) für dieses SzenarioDa Ihre Plattform über die administrative API aktiven Lese- und Schreibzugriff auf die Endnutzerdaten hat, reicht ein Standard-DPA für „verschlüsselte Daten im Ruhezustand (Data at Rest)“ nicht aus. Folgende spezifische Regelungen müssen im DPA (nach Art. 28 DSGVO) verankert werden: [1] (https://www.atlassian.com/blog/development/data-processing-agreements-dpas-developer-info), [2] (https://payproglobal.com/answers/what-is-dpa-agreement-in-saas/)Erweiterter Gegenstand und Art der Verarbeitung (Anlage 1): Es muss explizit festgehalten werden, dass die Verarbeitung nicht nur das Speichern/Hosting umfasst, sondern das „Auslesen, Modifizieren, Sperren und Verwalten von Identitäts- und Sitzungsdaten über programmgesteuerte Schnittstellen (APIs) zu administrativen Zwecken“. [1] (https://www.back4app.com/product/parse-gdpr), [2] (https://www.atlassian.com/blog/development/data-processing-agreements-dpas-developer-info)Spezifische technische und organisatorische Maßnahmen (TOMs / Anlage 2): Da Ihre Plattform Code ausführt, der die Daten im Klartext verarbeitet, fordern Kunden hier präzise Sicherheitsnachweise:Audit-Logging auf Plattformebene: Protokollierung, welcher Mitarbeiter Ihrer Plattform (oder welches automatisierte Skript) wann die Admin-API eines Kunden aufgerufen hat.Mandantentrennung (Multi-Tenancy Isolation): Nachweis, dass die Admin-API von Mandant A unter keinen Umständen Daten von Mandant B abrufen kann.Verschlüsselung "In Transit": Zwingender Einsatz von TLS für alle API-Aufrufe. [1] (https://payproglobal.com/answers/what-is-dpa-agreement-in-saas/), [2] (https://www.atlassian.com/blog/development/data-processing-agreements-dpas-developer-info)Unterstützung bei Betroffenenrechten (DSAR): Wenn ein Endnutzer des Kunden von seinem „Recht auf Vergessenwerden“ (Löschung) Gebrauch macht, muss im DPA geregelt sein, wie Ihre Plattform dem Kunden hilft, diese Daten auch über das Admin-Dashboard/die API konsistent zu löschen. [1] (https://sisl.pl/en/blog/dpa-agreements-small-saas), [2] (https://payproglobal.com/answers/what-is-dpa-agreement-in-saas/)3.
